# 08 — Quality, evaluations, telemetry

CodeQL has run on millions of repos for years. We have anecdotes.
Closing that gap is mostly about benchmarks, eval harnesses, and
opt-in telemetry. **Without these, every claim of "we beat CodeQL on X"
is unverifiable.**

---

## §QE-1 — OWASP Benchmark integration

- **Why:** OWASP Benchmark is the standard SAST evaluation suite for
  Java. CodeQL has published numbers; we have none.
- **Current state:** No benchmark.
- **Target state:** A `tool/benchmark.sh` script that:
  1. Clones the latest OWASP Benchmark.
  2. Runs our scanner on it.
  3. Computes precision / recall / F-score per CWE.
  4. Outputs a leaderboard-format result.
- **Approach:** OWASP Benchmark ships labeled tests. Match our findings
  to its expected-results CSV.
- **Dependencies:** Java rule coverage ([01-language-coverage.md §LC-6+](01-language-coverage.md))
  for the benchmark to be meaningful.
- **Effort:** **L** (~2 weeks).
- **Tests:** CI runs the benchmark on every PR; fail if F-score
  regresses by > 1%.
- **Risks / gotchas:** Until §LC-6 lands, our F-score on OWASP
  Benchmark will be near zero. Document that.

## §QE-2 — Juliet (NIST) test suite

- **Why:** NIST's Juliet has 100k+ labeled C/C++/Java/C# test cases
  across CWE classes.
- **Current state:** None.
- **Target state:** Per-language: download Juliet, run scanner, score.
- **Approach:** Juliet has a known structure (one CWE per directory,
  positive/negative cases per file). Match to findings.
- **Dependencies:** Per-language coverage from
  [01-language-coverage.md](01-language-coverage.md).
- **Effort:** **L** (~3 weeks per language pack).

## §QE-3 — SARD (Software Assurance Reference Dataset)

- **Why:** SARD is broader than Juliet, covers JS/Python.
- **Current state:** None.
- **Target state:** Same as §QE-2 but for SARD-JS / SARD-Python.
- **Effort:** **L**.

## §QE-4 — Real-CVE corpus

- **Why:** Synthetic benchmarks miss real-world signal. CodeQL is
  trained on real CVEs.
- **Current state:** None.
- **Target state:** A curated set of 100 real CVEs in OSS Node
  packages, each with the vulnerable+patched versions. Scanner runs
  on vulnerable versions; assert it catches at least N% of them.
- **Approach:** Pull from GitHub Advisory Database. Each entry: package
  name, vulnerable version, patched version, CWE, file:line of the fix.
- **Effort:** **L** (~4 weeks for the initial 100 CVEs; ongoing
  maintenance).
- **Tests:** CI runs the corpus on every PR.

## §QE-5 — Public scoreboard / leaderboard

- **Why:** Transparency about precision is itself a competitive
  advantage. CodeQL doesn't publish per-rule precision.
- **Current state:** None.
- **Target state:** A web page showing per-rule precision/recall on
  each benchmark, updated on every release.
- **Approach:** Static site generated by CI; one HTML per benchmark.
- **Dependencies:** §QE-1, §QE-2, §QE-3, §QE-4.
- **Effort:** **M** (1 week post the benchmarks landing).

## §QE-6 — FP / FN tracking via suppression patterns

- **Why:** Production telemetry: a rule with many `// sast-ignore`
  comments has FP risk; one with a pattern of being added on a CVE
  fix has FN risk.
- **Current state:** Telemetry stores scan summaries; no per-rule FP
  estimate.
- **Target state:** Aggregate suppression-comment counts per rule per
  scan. Track over time. Surface "noisy rules" warning to the user.
- **Approach:** Already partly in [04-precision.md §PR-15](04-precision.md).
  Add to telemetry payload.
- **Effort:** **S** (2 days).

## §QE-9 — Bug bounty for confirmed FNs

- **Why:** Crowdsource the FN-finding work. CodeQL doesn't do this.
- **Current state:** None.
- **Target state:** Document a process: report a vulnerable code
  pattern that we miss, get credit / swag / cash. Add the pattern as
  a regression test.
- **Approach:** Document. Run on a budget if any.
- **Effort:** **S** (a few hours of process design + ongoing review).

## §QE-10 — Differential testing against CodeQL

- **Why:** When CodeQL flags a finding we don't, that's a high-signal
  hint of a missing rule.
- **Current state:** None.
- **Target state:** A `tool/differential.sh` runs both scanners on a
  shared corpus and surfaces:
  - Findings only CodeQL has → likely a coverage gap on our side
  - Findings only we have → potential wins (for the comparison doc)
- **Approach:** SARIF in, SARIF out, set difference by partialFingerprint.
- **Dependencies:** Requires CodeQL CLI installed locally / in CI.
- **Effort:** **M** (3 days).

## §QE-11 — Differential testing against Semgrep

- **Why:** Semgrep is closer to our shape (regex/AST patterns).
  Comparison reveals gaps in our rule library.
- **Effort:** **M** (3 days).

## §QE-12 — ML-ranked findings

- **Why:** A real differentiator. CodeQL doesn't do this.
- **Current state:** Findings ordered by severity then file/line.
- **Target state:** A small classifier ranks findings by likelihood
  of being a true positive based on:
  - source-to-sink path length
  - barrier presence between source and sink
  - test-path proximity
  - file age (stable code less likely to be vuln)
  - cwe class historical FP rate from telemetry
- **Approach:**
  1. Collect labeled examples (TP/FP) from §QE-4 corpus.
  2. Train a logistic regression / gradient-boosted model on
     hand-engineered features.
  3. Use as a `rank` field in SARIF (`automationDetails`).
- **Dependencies:** §QE-4, §QE-8.
- **Effort:** **L** (~3 weeks).
- **Risks / gotchas:** ML models drift. Re-train on every release.
  Document the features so they're auditable. **Don't** use the
  classifier to suppress findings — only to rank them.

## §QE-13 — AI-assisted explanation generation

- **Why:** Today our `confidenceReason` is templated. An LLM-generated
  explanation referring to the actual code is more compelling.
- **Current state:** Templated.
- **Target state:** Optional `--explain` CLI flag uses the user's
  configured LLM API to generate per-finding explanations.
- **Approach:** Each finding's `pathSteps` + source code slice → LLM
  prompt → markdown explanation attached to the finding.
- **Dependencies:** None.
- **Effort:** **M** (1 week).
- **Risks / gotchas:**
  - Privacy — source code leaving the user's machine. Off by default.
  - Cost — generate only on request.
  - Quality — LLMs hallucinate; pin a specific instruction template.

## §QE-14 — AI-assisted fix generation

- **Why:** Today's autofixes are 5 patterns. An LLM can generate a
  custom fix for any finding.
- **Current state:** None.
- **Target state:** Optional `--fix-with-ai` flag. Same caveats as §QE-13.
- **Effort:** **M** (1 week post §QE-13).

## §QE-15 — Reproducibility: deterministic scans

- **Current state:** Mostly deterministic, but some Set/Map iteration
  orders may not be.
- **Target state:** Audit + sort all output deterministically.
- **Effort:** **S** (1 day).

## §QE-19 — Soundness statement per rule

- **Why:** "Sound" means "no false negatives." Almost no SAST is sound.
  Honest rules state which one they aim for.
- **Target state:** Each rule declares `soundness: 'precise' |
  'complete' | 'best-effort'` in its metadata. Visible in scan output.
- **Effort:** **M** (3 days).

## §QE-20 — Public CHANGELOG with precision deltas

- **Target state:** Every release notes per-rule precision change.
- **Effort:** **S** ongoing.

## §QE-21 — Coverage gap reporting

- **Target state:** `flutter-supabase-helper coverage <repo>` reports
  which rules are well-tested-against vs absent in the repo's
  language stack.
- **Effort:** **M** (1 week).

## §QE-22 — Fuzz the engine

- **Why:** Defend against catastrophic regex / AST inputs that hang
  the scanner.
- **Current state:** Implicit via the iterative `walkAst` depth
  guard.
- **Target state:** Use jsfuzz / atheris to fuzz the scanner with
  random source files. Catch hangs / crashes.
- **Effort:** **M** (1 week).
